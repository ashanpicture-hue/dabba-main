# Dabba — Code Data-Practices Audit (Phase 3)

**Date:** 2026-11-02
**Product:** Dabba — preorder links for home bakers in Pakistan
**Codebase:** `E:\dabba-main`
**Stack:** Vite + React 18 + React Router 6, Supabase (Postgres + Auth + Storage), Vercel Analytics + GA4, OpenStreetMap Nominatim
**Auditor:** compliance-auditor skill (code-analyzer lane)

**Methodology:** Every factual claim below cites `file:line`. Where the code does not clearly support a claim, the auditor states the uncertainty explicitly. No behavior is inferred beyond what the code shows.

## 1. User registration & authentication

**What the code does:**
- Baker sign-in uses email via Supabase Auth OTP (one-time sign-in link, no password).
- `src/pages/Login.jsx:23` — `api.signIn(email.trim())` calls Supabase `signInWithOtp`.
- `src/lib/api.js:144` — `sb.auth.signInWithOtp({ email, options: { emailRedirectTo: `${location.origin}/app` } })`.
- Sign-in redirect goes to `/app` (the baker dashboard).
- In demo mode (`src/lib/api.js:68`), `session()` returns `{ email: "demo@dabba.pk" }` if `localStorage` has `dabba-demo-auth`; `signIn()` sets that flag.
- No customer registration or customer accounts exist. Customers place orders without signing in.
- No password collection, no social login (Google/Apple/etc.), no OAuth.

**Uncertainty:** None. Email is the only identifier collected for authentication, and only for bakers.

- `src/supabase/schema.sql` — `orders` table includes `customer_name`, `customer_phone`, `address`, `proof_path`, `lines`, `request`, `photos`.

**Uncertainty:** None. Shop profile and per-order customer data are fully enumerated in the schema.

## 3. Order / transaction data

**What the code does:**
- `src/pages/Shop.jsx:152-168` — `submit()` builds a draft with `due_date`, `zone`, `fulfilment`, `customer_name`, `customer_phone`, `address`, `notes`, then calls `api.placeOrder`.
- `src/lib/api.js:89-98` (demo) and `api.js:169-173` (live) — `placeOrder` creates an order record with customer details, line items, pricing, deposit, and optional payment proof.
- `src/pages/Request.jsx:59-70` — `submit()` builds a custom cake request with `occasion`, `servings`, `flavour`, `details`, up to 3 photos, delivery/pickup details, calls `api.requestCustom`.
- `src/lib/api.js:99-107` (demo) and `api.js:174-180` (live) — `requestCustom` creates a custom request order with photos and request details.
- `src/pages/Status.jsx` — order tracking page shows order code, date, fulfilment, items, total, deposit status, payment status, request details, and a WhatsApp link to the baker.
- `src/supabase/schema.sql` — `orders` table: `id`, `shop_id`, `code`, `created_at`, `due_date`, `fulfilment`, `zone`, `delivery_fee`, `address`, `customer_name`, `customer_phone`, `notes`, `lines`, `subtotal`, `total`, `deposit_due`, `units`, `proof_path`, `payment_status`, `status`, `request`, `photos`, `quote_note`, `quote_expires`.
- **Dabba never receives, holds, or moves money.** `src/pages/Privacy.jsx:46` — "Customers pay bakers directly by bank, Raast or wallet. Dabba never receives, holds or moves money, and never asks for card numbers." Payment screenshots are uploaded as proof but Dabba does not process payments.

**Uncertainty:** None. Order data fields are fully enumerated.

**Uncertainty:** None. Upload buckets (`proofs`, `mock`/`menu`) and paths are defined in code.

## 5. Analytics & tracking

**What the code does:**
- `src/lib/analytics.js` — GA4 wrapper. `initGA4` loads `googletagmanager.com/gtag.js` with measurement ID. `trackPage`, `trackEvent`, `trackConversion` send events.
- `src/main.jsx:30-32` — GA4 initialized only `if (choice?.analytics)`. `<Analytics />` from `@vercel/analytics/react` rendered only `if (choice?.analytics)` (line 50).
- `src/lib/consent.js` — consent stored in `localStorage` key `dabba-consent-v1`, single boolean `analytics`, max age 1 year (365 days).
- `src/components/CookieBanner.jsx` — banner offers "Decline" and "Accept analytics" buttons. Nothing runs until user accepts.
- `TRACKING_PLAN.md` — Events: `page_view`, `cta_clicked`, `form_submitted`, `signup_completed`, `shop_created`, `order_placed`, `custom_request_sent`, `order_tracked`, `payment_proof_uploaded`, `menu_item_added`, `date_selected`. Custom dimensions: `user_type`, `plan_type`, `city`. GA4 retention: 14 months. IP anonymization enabled. No PII in properties.
- `src/lib/analytics.js:23` — `anonymize_ip: true` set in GA4 config.

**Uncertainty:** None. Consent gating and event list are explicit in code and tracking plan.

## 8. Data retention

**What the code does:**
- **No server-side retention policies exist.** No TTL, no scheduled deletion, no `deleted_at` soft-delete, no retention period defined in `supabase/schema.sql` or any API function.
- `src/lib/consent.js:5` — Consent choice expires after 1 year (user is asked again).
- `TRACKING_PLAN.md:50` — GA4 data retention: 14 months (GA4 default, set on Google's side, not Dabba's code).
- `src/lib/api.js:128` — `demo.reset()` removes `dabba-demo-v3` from localStorage (demo only).
- No `deleteAccount`, `deleteShop`, `deleteOrder`, or `deleteUser` function exists in `api.js`.
- `src/pages/Dashboard.jsx` — bakers can delete menu items (`deleteItem`) and close their shop (`is_open = false`), but no account deletion or data erasure function exists.

**Uncertainty:** High. The code has NO retention logic. The privacy policy must not claim specific retention periods unless they are implemented. Honest hedging: "We keep data as long as your account is active" or similar, with no concrete period.

## 9. User rights (access, erasure, portability)

**What the code does:**
- **No self-service data export endpoint exists.** No `/api/export`, no download-my-data function.
- **No self-service data deletion endpoint exists.** No `/api/delete-account`, no erasure function.
- `src/pages/Privacy.jsx:52` — "Ask the bakery to correct or delete your order, or use the feedback button to ask us to delete your data." This is a manual process, not automated.
- `src/components/Feedback.jsx` — feedback form can be used to request deletion, but it sends a feedback record, not a deletion command.
- Order status page (`src/pages/Status.jsx`) lets customers view their own order by code (read-only access to their own data).
- Bakers can view their own orders via `api.orders(shopId)` (RLS-scoped to their shop).

**Uncertainty:** High. User rights must be handled manually (email the developer). The policy should say "contact us" rather than "self-service export."

## 11. International transfers

**What the code does:**
- `src/pages/Privacy.jsx:49` — "The website runs on Vercel. Order data, files and sign-in run on Supabase. Both may store data outside Pakistan."
- Vercel: US-based hosting provider. `vercel.json` deploys to Vercel.
- Supabase: cloud Postgres; region depends on project selection (user chooses region when creating Supabase project). Could be US, EU, or other.
- Google (GA4): US-based. `src/lib/analytics.js` loads `googletagmanager.com`.
- OpenStreetMap Nominatim: UK-based (OpenStreetMap Foundation). `src/lib/geocode.js:10` sends address text to `nominatim.openstreetmap.org`.
- No Standard Contractual Clauses, no DPF certification, no transfer mechanism documented in code.

**Uncertainty:** Medium. Supabase region is user-selected at project creation; Dabba code does not enforce a region. The policy should state data may be stored outside Pakistan without specifying exact countries.

## 12. Security

**What the code does:**
- `src/supabase/schema.sql` — Row Level Security (RLS) policies on `shops`, `items`, `orders`, `feedback` tables. Security-definer functions (`place_order`, `request_custom`, `accept_quote`, `order_status`, `day_load`) re-validate prices, dates, capacity on server.
- `src/supabase/schema.sql` — `proofs` storage bucket is private; signed URLs expire after 600 seconds (`src/lib/api.js:190`).
- `src/lib/api.js:142` — `must()` helper throws on Supabase errors.
- `src/lib/api.js:149` — handles unique violation (23505) for duplicate slugs.
- No admin access log visible in code. No `ADMIN_EMAILS` env guard found.
- No CSP headers configured in `vercel.json` (only SPA rewrite).
- No HSTS configured.
- `src/main.jsx:50` — `@vercel/analytics` loaded conditionally.
- Feedback submissions include `page: location.pathname` (`src/components/Feedback.jsx:19`).

**Uncertainty:** Medium. RLS exists but the exact policy definitions need to be read from `schema.sql` (file is large). No security headers beyond what Vercel provides by default.
